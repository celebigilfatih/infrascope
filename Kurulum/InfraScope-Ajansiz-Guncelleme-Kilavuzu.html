WINDOWS 11 · DOCKER DESKTOP · MEVCUT 1.0.9 KURULUMUNDAN GÜNCELLEME

InfraScope ajansız güncelleme

Yeni sürümü GitHub Releases ve GHCR’ye yayımla; müşteriye uzaktan bağlanıp mevcut güncelleme betiğini çalıştır.

Her müşteri için aynı yöntem kullanılır. Hedef sürümü sen seçersin; güncellemeyi bakım zamanında sen başlatırsın. Ajan kurulumu gerekmez.

1. Müşteride çalıştırılacak iki komut

Windows VM’ye uzaktan bağlan. Docker Desktop’ı çalıştıran kullanıcıyla PowerShell aç. Docker’ın Linux konteyner motoru açık ve internet bağlantısı erişilebilir olmalı.

Mevcut kurulumun C:\InfraScope\infrascope konumunda olduğunu ve kurtarma parolası dosyasının C:\Private\infrascope-recovery-passphrase.txt yolunda bulunduğunu doğrula. Farklıysa komuttaki yolları düzelt. Parola dosyası mevcut yedekleme için kullandığın, en az 16 baytlık tek satırlık UTF-8 dosya olmalı.

Bakım zamanı: Mevcut 1.0.9 betiği yedeği aldıktan sonra app/NMS servislerini durdurur. Yedek başlamadan önce kullanıcı işlemlerini, entegrasyon ve harici DB yazmalarını durdur; güncelleme tamamlanana kadar yeniden başlatma. Yedekten sonra yapılan yazmalar kurtarma noktasında bulunmaz.
Müşteri VM’sinde · PowerShell
Set-Location 'C:\InfraScope\infrascope'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\update.ps1 -Version (Read-Host 'Yayımlanan hedef sürüm (başında v olmadan)') -PassphraseFile 'C:\Private\infrascope-recovery-passphrase.txt'

Sorulduğunda GitHub Releases sayfasında gerçekten yayımlanmış hedef sürümü yaz. Biçim örneği: 1.0.10; bu örnek, o sürümün yayımlandığı anlamına gelmez. v öneki veya latest yazma.

Betik paket ve dosya özetlerini doğrular, sabitlenmiş imajları indirir, zorunlu şifreli yedek alır ve güncellemeyi uygular. Mevcut veritabanı, ayarlar, lisans ve makine kimliği korunur; .env içinde yalnız VERSION güncellenir.

Başarıyı kontrol et

Update complete mesajını ve servis sağlığı sonucunu gör. Uygulamayı http://localhost:8170 adresinde aç; müşteri verileri ve kullanılan entegrasyonları kontrol et. Özel port kullanılıyorsa kendi adresini aç. Ekranda belirtilen .isbackup yedeğini VM dışındaki güvenli depoya kopyala; parolayı ayrı sakla.

Gerekirse servisleri şu komutla kontrol et:

İsteğe bağlı · servis kontrolü
docker compose -f docker-compose.yml -f release-images.yml ps

Hata olursa başka sürüme geçme. Nedeni giderip aynı hedef sürüm ve parola dosyasıyla aynı güncelleme komutunu yeniden çalıştır. .update-state.json dosyasını silme; migration sonrasında sürümü elle düşürme. .env, data veya Docker volume’lerini silme. Geri yükleme gerekiyorsa kurulumdaki BACKUP_OPERATIONS.md adımlarını izle.

2. Yeni sürümü yayımlama

Bu bölüm geliştirme bilgisayarında uygulanır.

  1. Değişiklikleri gözden geçirip commit et ve main dalına birleştir. Genel regresyon, TypeScript, lint, güvenlik ve üretim derlemesi kontrollerinin hedef commit için geçtiğini doğrula.
  2. Güncel ve temiz main üzerinde, origin/main ile aynı commit’te olduğundan emin ol. Yeni ve kullanılmamış bir sürüm numarası seç. Aşağıdaki bloğu yalnız yayın hazır olduğunda çalıştır; etiketin push edilmesi yayını başlatır.
Geliştirme bilgisayarı · depo klasöründe PowerShell
$Surum = Read-Host 'Yeni sürüm numarası (başında v olmadan)'
if ($Surum -cnotmatch '^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$') { throw 'Geçerli bir X.Y.Z sürümü girin.' }
git tag -a "v$Surum" -m "InfraScope $Surum"
if ($LASTEXITCODE -ne 0) { throw 'Etiket oluşturulamadı; yayına devam etmeyin.' }
git push origin "v$Surum"
if ($LASTEXITCODE -ne 0) { throw 'Etiket gönderilemedi; GitHub durumunu kontrol edin.' }
  1. Publish InfraScope Image iş akışını izle. İş akışı kalite ve regresyon kapılarından sonra app/NMS imajlarını yeniden derleyip GHCR’ye gönderir; kurulum ZIP’ini, HTML/PDF kılavuzlarını ve SHA-256 dosyalarını hazırlar.
  2. İş akışının tamamının başarılı olduğunu ve Release sayfasında hedef sürümün altı dosyasının bulunduğunu doğrula. İmaj derlemesinin bitmesi tek başına yayın tamamlandı demek değildir. Mevcut herkese açık dağıtımda müşterinin GitHub tokenı kullanması gerekmez.
  3. Yayımlanan sürümü önce test kurulumunda güncelle. Ardından bir pilot müşteride uygula ve doğrula; kalan müşterilerde aynı iki komutu bakım zamanlarında çalıştır.
Her değişiklik için yeni sürüm: Yayımlanmış etiketi veya dosyaları değiştirme. Yeni kod için yeni sürüm yayımla; mevcut iş akışı aynı Release’in üzerine yazmayı reddeder.

Birden fazla müşteri için basit bir kayıt tut: müşteri adı, önceki/hedef sürüm, güncelleme tarihi, sonuç ve yedeğin saklandığı yer. Aynı Release tüm müşterilerde kullanılabilir.
