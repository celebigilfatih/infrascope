# Security policy workspace

`/security/policies` uses the shared heading, icon, status badge and workspace styles. Select a saved FortiGate configuration and VDOM before reading definitions. The same configuration can expose separate VDOM options; selection keys include both fields. Disabled configurations do not initiate source reads.

`GET /api/firewall-policies/workspace` requires the current ACTIVE account's `firewall/read` permission and explicit `configId`, `vdom` and observed `expectedHost`. The shared connector factory resolves the saved connection and VDOM. A changed host/VDOM is rejected before the policy request. Successful responses include exact scope, FortiGate REST provenance, collection time and `private, no-store` headers. The UI validates the scope and snapshot shape and cancels/ignores superseded client reads. This path performs no writes, synchronization or approval-policy changes.

The workspace reads policy definitions with the existing optional strict service mode: disabled policy modules and SNMP-only mode fail explicitly. A missing/malformed list or duplicate/missing policy identity does not become a successful empty result. The old cache-oriented endpoint and other consumers retain their contracts. The new view does not use the device-only database policy cache as current VDOM evidence, since that schema cannot identify a complete VDOM-specific snapshot.

Each row separates rule state (enabled/disabled/unknown) from configured action (accept/deny/other/unknown). Missing or empty address, service and interface lists never imply all. Only explicit `all`, `ALL` and `any` names receive context-specific Turkish descriptions; address groups are listed by name without claiming their member expansion. Optional comments, NAT and traffic logging fields are carried through the shared source reader.

The source array order is preserved, and displayed position refers to that returned list. Policy ID is a stable identity, not evaluation priority. Cards and local searches/filters summarize returned definitions, not effective protection or all possible IPv6/implicit policy families. Search covers full returned address/service lists, including items abbreviated in table cells. Paging shows ten filtered rows at a time; source reads do not repeat for each search keystroke.

Missing hit counts remain unknown. Safe integer numbers and canonical decimal strings retain exact values; unsafe numeric values are not rounded into a claimed count. Explicit zero stays zero. Last-use dates require a supported ISO timestamp with an explicit zone; ambiguous or unsupported source formats remain unknown. Dates display in Turkey time. The source counter interval is unknown and is stated in details; no unused/effective/live-traffic claim is inferred from counters or rule action.

Same-scope refresh failures retain clearly marked previous definitions. Source changes remount the view, clear old details and prevent late responses from entering another scope. Mobile cards and scrollable details use the same data and support light/dark themes, long names and IPv6 addresses.

Validation: `node scripts/check-security-policies.cjs` runs the actual model, strict service method, target factory and read route with synthetic DB/transport only. It covers scope/host/disabled/permission/SNMP/module gates, safe failures, exact counters, empty/missing lists, optional details, date validation and no persistence. Related VIP, quarantine, connector-scope and 55 SNMP regressions are also run. Browser checks use the real page component in `output/policies-refresh` with an isolated transport and an explicit TEST VERİSİ banner. The current installation has no saved FortiGate configuration, so the live setup state is separately verified without creating an appliance or changing settings.
