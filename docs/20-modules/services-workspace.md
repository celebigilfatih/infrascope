# Services workspace

`/services` uses the common Turkish heading, icons, semantic status badges, summary cards, local search/filters, ten-row paging, responsive cards and an accessible detail dialog with service/relationship tabs. It shows real service records, including services without an assigned application, and replaces the former first-50 card list and inactive detail/add controls.

## Read boundary and evidence

`GET /api/services/workspace` uses the existing current ACTIVE actor and `devices/read` policy. A repeatable-read transaction reads the complete service list with selected application identity, hosting device and outgoing relationship target identity. More than 20,000 services or 50,000 relationships fails explicitly before the nested read; no truncated snapshot is presented as complete. The shared Prisma client performs no source probes or writes. Existing paginated `/api/services` and its other consumers retain their contracts.

Responses carry `database` provenance, a reading time, `private, no-store`, and a `canDelete` flag derived from the current role. License keys, installation paths, service metadata and device credentials are not selected. The parser validates unique service/relation IDs, nullable application identity, matching hosting/target device IDs and each relationship's source service ID. Missing lists/mismatched relations fail rather than becoming zero; missing/unrecognized status remains UNKNOWN and invalid ports/protocols/timestamps remain unknown. Explicit null application means unassigned, not unavailable data.

The screen shows **recorded service state**, not live health. Status and importance are labelled separately; application/hosting-device health is not inferred from service status. Summary counts include all returned records: total, running, failed/degraded/stopped requiring review, and relationship edges. Unknown-state and unassigned counts are separately stated. Dates use Europe/Istanbul with TSİ labels. Record update time and list read time are distinct; neither is presented as a last health check.

Relationships are **source service → saved relationship type → target device**. Their types and importance remain separate; the target is not inferred to be another service/application. Multiple edges to one device count as multiple relationships but one unique target. All targets, including abbreviated entries, participate in search and appear in the detail tab. A successful empty relationship list means no saved relations, not no actual dependencies. There is no incoming or transitive dependency inference.

Filters cover recorded status, exact assigned application (or unassigned), and relationship presence. Search covers full service/application/device/target names, IPs, ports, descriptions and Turkish type/status/relationship labels. Filtering does not issue another source read. Failed refreshes retain labelled previous results and original reading time; aborted/superseded requests cannot overwrite newer results. Refresh closes old detail panels.

## Existing record deletion

The existing DELETE `/api/services/[id]` and its dependency guard remain in use. The handler now rechecks the current ACTIVE actor with the existing `devices/delete` policy; only ADMIN has this permission. Existing HTTP status/identity contracts are preserved and delete-facing messages are Turkish. The delete transaction takes a parameterized FOR UPDATE lock on the service row before reading relationships, at ReadCommitted isolation. This blocks concurrent foreign-key inserts/record edits until the check/delete completes. A dependency committed while deletion waits is read after lock acquisition and blocks deletion. The UI sends expectedUpdatedAt and disables deletion for an unknown record timestamp; stale versions return 409. Invalid calendar dates return 400. Legacy callers may omit the optional version parameter.

The detail dialog exposes record deletion only when permitted. Existing relationships, stale/unavailable reads, in-flight actions or uncertain outcomes disable deletion. Confirmation shows the exact service, application, host and port/protocol, and explains that deleting inventory does not stop the real service. A synchronous lock prevents duplicate submissions; the dialog stays controlled while pending. A successful ID-specific acknowledgement plus a fresh snapshot confirming absence is required before reporting verified deletion. Otherwise the UI marks the result uncertain and prevents blind retries until a successful explicit refresh. Read rendering is independent of deletion.

## Verification

`npm run test:services-workspace` executes the real model/current-actor/permission/read/delete paths against synthetic persistence. `tests/incident-e2e/services-workspace.spec.ts` covers full snapshots, exact private/no-store policy, current roles and stale admin cookies, invalid identities, paging/search/details, retained failed reads, calendar validation, duplicate-submit/read-back guards, legacy/versioned deletion and concurrent PostgreSQL relationship protection. `lint-regressions.spec.ts` follows the new service workspace; the pending dependencies redesign is outside this commit. Current verification results and isolation are recorded in design-qa.md. No live source probes or customer record writes are needed.

Commit verification (20 October 2026): 40/40 Chromium cases, strict full lint, TypeScript and offline release build passed. The real PostgreSQL blocked-delete test preserves a concurrently committed dependency; removing the lock is rejected by the same regression. Detailed evidence and the initial locator correction are in design-qa.md.
